#+date: 2026-10-18
#+startup: overview
#+options: toc:2 num:nil

* What now works

The existing pinned TinyCC command-line compiler runs as a static native
executable in its own world, linked against the shared Low libsa. It reads
source and headers through the BSD service and writes ordinary ELF object
files. The existing Lisp linker combines those with startup, compiler
support objects and libsa to produce another native executable.

This is the upstream tcc.c driver, not a replacement command parser or a
remote compiler. No TCC source patch was needed. The source revision is
43c7708b85681a2fd4451c8a541af4494a8919b2, already pinned by manifest.scm.
The upstream version banner says x86_64 Linux; the executable actually
uses Darterfly's libsa and trap ABI. The build options explicitly undefine
the Linux/Unix target macros when compiling Darterfly sources.

The compiler can rebuild its own C/assembly sources and support objects
from inside its native world. Low still builds libsa and Lisp still links
the executable. That is a local compiler rebuild, with the Lisp system
acting as build coordinator and linker.

* The bootstrap sequence

#+begin_example
embedded TCC already in the booted image
    |
    | compile upstream tcc.c, crt0.S and libtcc1 support
    | Low builds libsa; Lisp links the native executable
    v
standalone TCC seed, in its own world
    |
    +---- compile a C program -> Lisp link -> run another world
    |
    +---- compile TCC and support -> Low/Lisp link -> rebuilt TCC
                                                     |
                                                     +-- compile/run client
                                                     +-- build next generation
#+end_example

The seed itself is produced inside Darterfly, rather than imported as an
additional host-built executable. Once the seed exists, the standalone
compiler handles every C/assembly unit in the subsequent compiler build.
No call to the embedded compile-c path is needed in those later stages.

libtcc1 supplies compiler-generated arithmetic, varargs, atomic and alloca
helpers. These are the same pinned sources already used by Darterfly's
TCC-built runtime. They supplement libsa; they do not introduce another
libc, allocator, TLS implementation or descriptor service.

* Use it in the running OS

These functions run inside Darterfly. The normal source-bearing root disk
must contain /usr/src/darterfly and /usr/lib/tcc/include. Choose persistent
output/work paths to retain the compiler and its support objects.

#+begin_src lisp
(multiple-value-bind (compiler support)
    (darterfly/cc:build-native-tcc
     "/Users/darterfly/tools/tcc"
     :work "/Users/darterfly/build/tcc-seed/"
     :verbose t)
  (unless (darterfly/cc:compile-native-c
           compiler "/Users/darterfly/hello.c"
           "/Users/darterfly/build/hello.o" :compat nil)
    (error "C compilation failed"))
  (darterfly/cc:link-native-program
   "/Users/darterfly/tools/hello"
   (cons "/Users/darterfly/build/hello.o" support))
  (let ((p (sb-ext:run-program
            "/Users/darterfly/tools/hello" nil
            :search nil :output *standard-output* :error *error-output*)))
    (unwind-protect (sb-ext:process-exit-code p)
      (sb-ext:process-close p))))
#+end_src

The second value from build-native-tcc is the list of startup and compiler
support object paths. Keep that list, or save it with the build metadata,
for subsequent program links. link-native-program adds the existing libsa
object itself and marks its output executable.

Rebuild the compiler using the standalone seed:

#+begin_src lisp
(darterfly/cc:build-native-tcc
 "/Users/darterfly/tools/tcc-rebuilt"
 :compiler "/Users/darterfly/tools/tcc"
 :work "/Users/darterfly/build/tcc-stage2/"
 :verbose t)
#+end_src

compile-native-c returns success and the child status. It accepts include
paths, definitions, a working directory and diagnostic/output streams.
A failed compilation removes the output object so an old artifact cannot
masquerade as the result of the failed build. Use absolute compiler and
working-directory paths in build recipes.

* Actual-OS verification

#+begin_src sh
make test-native-tcc-guest
make test-native-tcc-large-guest
#+end_src

The test boots the real Darterfly image in four-vCPU QEMU with a disposable
root disk. All compiler generation, linking and artifact execution after
boot happens in that OS. Transcripts are build/native-tcc-guest.log and
build/native-tcc-large-guest.log. See [[file:VALIDATION.org][the validation record]] for the executed results.

The tests cover compiler startup; its live native-world identity while
blocked on stdin; preprocessing from a pipe; explicit diagnostics and
failed-output cleanup; relative source/output paths with a chosen cwd;
compiling and running a client; rebuilding TCC and its support objects;
using the rebuilt compiler; and a further generation with an exact binary
comparison. The client allocates memory, writes a verified artifact and
returns a checked exit status. An isolated Lisp build driver also compiles,
links and launches a client through the same public helpers.

A separate test compiles a data section larger than the 1 MiB transfer
limit, links it, and runs code that checks bytes at both ends. Shared
fwrite now finishes successful short writes: it loops until all elements
are written or an error occurs, and sets the stream error flag
on failure. The test also checks read-only output and size overflow.
The fix is in shared libsa and applies to every world.

* Boundaries still in place

- The tested mode is native TCC -c plus the existing Lisp linker. This
  does not qualify TCC's executable linker, -run, dynamic loading, plugins
  or cross-architecture driver re-execution. Compiler backtrace and bounds
  instrumentation are disabled through their existing build options.
- The source tree/configuration and generated tccdefs_.h are staged by
  the existing image build. Regenerating every source/configuration input
  from the Guix origin inside Darterfly is a further bootstrap-closure
  task. Binary agreement between local stages is a narrower claim.
- Native programs still inherit the shared runtime's documented limits,
  including bounded spawn arguments, static linkage, incomplete pthread
  cleanup and serial blocking services per process.
- The source and test root disk are deliberately small. Compiler source
  builds at LLVM/Chromium scale still need resource and filesystem tests.
- TCC does not close the C++ toolchain or browser-engine gates. Clang/LLD,
  the required C++ runtime and engine build generators remain unported.

* What follows

Use this compiler loop as a regression gate for further runtime work.
Qualify compiler-generated code and failure behavior against a broader C
corpus, and close the staged-input regeneration gap. Keep the compiler
support objects reproducible alongside their compiler and sysroot.

Proceed to a minimal selected C++ runtime workload and LLVM host-port
requirements. Add missing behavior to the shared runtime, preserving this
TCC build loop. The next compiler gate remains a native Clang/LLD seed,
a working C++ artifact, then a local compiler rebuild. The subsequent
engine and Nyxt gates remain in [[file:SELF-HOSTING.org][the browser self-hosting plan]].
