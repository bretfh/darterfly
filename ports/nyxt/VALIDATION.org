The final C++ probe is compiled with ordinary application flags. Target
compilation clears host include-path environment variables and uses the
explicit libsa/libc++/compiler builtin headers. This caught an accidental
host mbstate_t header dependency; the final build supplies that state type
from libsa. No host libc is linked into the target executable.

All guest suites boot the actual Darterfly image in four-vCPU QEMU. The
C++ runtime and probe objects are declared Guix-hosted Clang/LLD seed
inputs. Inside Darterfly, Low regenerates shared libsa, embedded TCC builds
startup, and the existing Lisp linker produces the executable. Native
Clang, native LLD and a local C++ source rebuild are not claimed.

The runtime probe passes initializer priority and global construction;
vector/string/sorting and shared/unique ownership; aligned allocation and
division-result ABI; new_handler, bad_alloc and nothrow allocation failure;
RTTI/demangling; cross-unit exceptions, automatic-object destruction and
exception_ptr rethrow; constructor-guard retry; four concurrent threads
with TLS destruction and exceptions; pthread key destructor iterations;
80 destructor registrations and idempotent DSO finalization; and clocks.

The exit artifact verifies main-thread TLS destruction before atexit and
global destruction, followed by the fini array. A custom terminate handler
returns the expected status for an uncaught exception. Two concurrent
instances produce independent artifacts and leave no native processes.

Initial OS tests exposed constructor boundaries preceding alignment
padding and omitted LLVM unwind sections. The linker now publishes aligned
array bounds, reads SHT_X86_64_UNWIND and ignores R_X86_64_NONE records.
The focused host regressions preserve these fixes. The TCC regression still
produces identical second/third compiler generations with the new runtime.

The sole complete-host failure remains the existing onboarding call to
undefined DARTERFLY/INSTALL::FIRST-START-ENTRIES. The runtime cross-build
also emits an upstream warning that this platform has no ELAST definition;
libc++ uses its generic strerror_r path. This is not a failed build or a
claim of complete error-message or standard-library coverage.
