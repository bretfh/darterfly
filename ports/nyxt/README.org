#+title: Nyxt compatibility work
#+startup: overview

* Preservation policy

Run upstream Nyxt and its existing backend as nearly unchanged as
possible. Follow the SBCL port model: implement platform facilities in
Darterfly and carry a small, explicit patch set where required. Replacing
Nyxt's UI, commands, persistence, or renderer wholesale is not the plan.

Base: f11c970. Branch: codex/nyxt-compat. The original networking worktree
is independent of this worktree. No Nyxt or cl-cef sources were changed.

* First increment: anonymous local stream pairs

The BSD service implements AF_LOCAL/SOCK_STREAM socketpair with two
bounded byte queues, blocking/nonblocking I/O, EOF, duplicate descriptor
lifetimes, and read/write shutdown. The foreign socketpair entry supports
SOCK_NONBLOCK and SOCK_CLOEXEC. F_GETFD/F_SETFD now expose the stored
close-on-exec bit. World calls marshal the two output descriptors through
appended service operation 49; existing operation numbers do not change.

The implementation lives in src/bsd/local-socket.lisp. Each direction
reuses the pipe-buffer storage and lifetime counters. Socket stream writes
can make partial progress without the atomic-write guarantee of pipes.

The low wrapper leaves the caller's descriptor array unchanged on errors.
Foreign descriptors start at three to avoid libsa's console handling.
Internet sockets now report unsupported shutdown instead of falsely
claiming a shutdown occurred; TCP half-close remains to be implemented.

This is deliberately a supported subset, not complete AF_UNIX support:

- Named socket creation/bind/connect/accept is still missing. That is
  required for Nyxt's existing startup socket and cl-electron transport.
- Datagram/seqpacket pairs, SCM_RIGHTS and credential passing are absent.
- Local getsockname/getpeername return EOPNOTSUPP in this increment.
- Foreign socket options and readiness/polling still need real semantics.
- Ordinary Lisp fork descriptor inheritance is not native engine exec.
- Isolation and resource quotas need qualification before hostile content.

* Validation

Host tests cover bidirectional byte streams, partial reads/writes,
buffering limits, duplicate lifetimes, half-close, nonblocking errors,
blocked-reader/writer wakeups, foreign flags, errno, and service replies.

The guest test compiles tests/socketpair-probe.c using Darterfly's TCC.
It runs the probe in the system world and an isolated world, exercising
the low C entry points and the actual port-vfs path. It also checks that
the system remains responsive after the isolated world exits.

Run =make test-local-sockets= for the host checks. Run =make sbcl= once
in a fresh worktree, then =make test-local-sockets-guest= for the guest.
The guest uses a disposable file-backed disk, not a physical device.
The existing host onboarding test FRESH-INSTALL-DOES-NOT-INHERIT-COMPLETED-
SETUP refers to undefined FIRST-START-ENTRIES at the parent revision.
Keep that pre-existing failure distinct from these compatibility tests.

See [[file:VALIDATION.org][recorded validation and limitations]].

* Next gates

1. Pin and reproduce the existing Nyxt/CEF host configuration. Keep the
   Guix Electron recipe as a separate behavior/dependency reference;
   its source pin differs from the current local Nyxt checkout.
2. Audit the selected engine's actual OS/build dependency closure. CEF's
   wrapper size does not represent the Chromium platform port size.
3. Implement named local sockets, readiness, and descriptor transfer with
   bounded data, lifetimes, cancellation, and cross-world tests.
4. Support the foreign libraries needed by the selected unchanged backend
   through a deliberate loading/linking strategy and correct ABI.
5. Add a world-facing graphics endpoint over the existing compositor.
   Prefer adapting the existing engine/backend platform integration over
   rewriting Nyxt or replacing cl-cef with an unrelated implementation.
6. Cross-build the engine for Darterfly, qualify native execution, then
   bring its complete source-build toolchain onto Darterfly.

A C++ compiler need not run on Darterfly to execute an externally built
engine. Cross compilation does not eliminate the engine OS port, and
complete suite self-hosting still requires its build closure locally.
