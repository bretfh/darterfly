* Use the inventory Guix already provides

Guix directly exports CycloneDX SBOMs. There was no need to reconstruct
its package inventory by hand. The exports beside this document are
produced by the installed Guix, using the pinned channels in channels.scm.

#+begin_src sh
  guix graph -L /home/bfh/dots/src \
    -e '(@ (dots packages nyxt) nyxt)' \
    --type=bag --backend=cyclonedx-json > nyxt.cdx.json
#+end_src

The bag graph includes implicit build dependencies. The package graph
omits implicit inputs; it is not a runtime-only graph. The installed
runtime closure is recorded separately with guix gc --requisites.

* Reproduce the exports

[[file:sbom/export.sh][Export script]] reproduces the package SBOMs and graphs.
[[file:sbom/channels.scm][Channel pins]] record the Guix and Nonguix revisions.
[[file:sbom/recipes/dots/packages/nyxt.scm][Nyxt recipe]] and
[[file:sbom/recipes/dots/packages/node-deps-nyxt.scm][Native Node dependency recipes]]
are captured so a subsequent local edit does not change this reference.
The export script loads these captured recipes.

#+begin_src sh
  guix time-machine -C ports/nyxt/sbom/channels.scm -- \
    graph -L ports/nyxt/sbom/recipes \
    -e '(@ (dots packages nyxt) nyxt)' \
    --type=bag --backend=cyclonedx-json > /tmp/nyxt.cdx.json
#+end_src

This reproduction command has not been executed with time-machine.
The export script was checked against the current pinned Guix instead.
Some channels use local repository URLs; those repositories must remain
available, or be replaced with accessible mirrors of the same commits.
The captured recipe files supplement rather than replace those channels.

Timestamps in CycloneDX exports will differ. Compare graph nodes, edges,
versions and channel revisions rather than byte equality of the JSON.
The installed closure belongs to the specific store path recorded in
[[file:sbom/provenance.json][provenance.json]]; it is not regenerated by export.sh.

No compiler or browser was built for this inventory. Guix graph evaluates
recipes and derives the graph; this is not proof of successful builds.

* What the recipes actually establish

** Nyxt currently means Electron in the Guix package

The local recipe selects NYXT_RENDERER=electron and pins Nyxt source at
641fd65824036965e24ed803698977e74b3afd3e. The separate Nyxt checkout is at
cfa068ea781fe4866ae435c2950c00c5ec51cfee. Do not treat them as identical.

The recipe supplies SBCL, Node and pkg-config as build inputs. Its runtime
inputs include Electron 36.9.5, Slynk, OpenSSL, libfixposix, SQLite,
Enchant and the synchronous-socket Node addon with its helper packages.
The Lisp dependencies arrive inside a recursively fetched source tree;
they are not all separate Guix package components in this recipe's SBOM.

Nonguix's electron-36 downloads an upstream release ZIP. Its dependency
graph describes packaging and surrounding libraries, not the complete
source build of the Chromium engine inside that ZIP.

** The packaged CEF is a reference, not a usable selection yet

Nonguix packages CEF 117.2.4, revision 5053a95, based on Chromium
117.0.5938.150. It downloads a minimal binary distribution and builds the
C++ wrapper. It does not build libcef from Chromium source.

The inspected cl-cef binding requires CEF 124 or newer. Its source is
pinned at 257c6421bb173cbe50d2b5a2a1066bace15347fc. Consequently, this CEF
recipe cannot simply be plugged into the current binding unchanged.
Updating the recipe and testing a compatible version is required.

** Guix already has a useful engine source-build reference

The pinned Guix packages ungoogled-chromium 147.0.7727.137-1, using a
Chromium source archive, patches and explicit system-library selections.
Its recipe exposes both the build flags and the native build tools:

| Function | Recipe selection |
|----------+------------------|
| C/C++ compiler | Clang 21.1.8 and its runtime/toolchain |
| Code generation and object tools | LLVM 21.1.8 |
| Linker | LLD 21.1.8 through the ld wrapper |
| Rust compiler | Rust 1.93.0 |
| Rust bindings | rust-bindgen-cli and rust-cbindgen |
| Build graph and executor | GN and Ninja |
| Generators | Python, its declared modules, Node 22.14.0 |
| Other build tools | Bison, gperf, pkg-config, which, Wayland tools |

The full versioned inventory and dependency edges are in the exports.
The recipe also lists graphics, font, codec, crypto and system libraries.
It explicitly disables some features, unbundles some libraries, and
retains selected third-party code within Chromium's source archive.

This is a concrete Linux source-build baseline for planning. It is not a
CEF build recipe, a Darterfly port, or a promise that the same settings
work unchanged with CEF. In particular, its system-toolchain patches and
build flags must be reconciled with the selected CEF/Chromium branch.

The default Guix clang/llvm/lld roots resolve to 22.1.8. The Chromium
recipe selects 21.1.8. A separate LLVM 21 export records that toolchain;
we should not choose LLVM 22 merely because it is the current default.

* CEF and the browser architecture

CEF embeds Chromium's browser implementation behind an application API.
Blink provides page layout and rendering; V8 executes JavaScript. CEF
also exposes browser lifecycle, navigation, networking and subprocess
integration. It can supply the engine for a real Nyxt browser.

CEF is not an independently implemented engine that avoids Chromium's
porting work. Nyxt supplies the Lisp application, commands and interaction
model. Its existing cl-cef backend is the integration layer. Chromium
still needs operating-system facilities beneath that layer.

The libcef interface includes a C API. That does not make its Chromium
implementation compilable with a C compiler. Moreover, the existing
cl-cef bridge uses C++20, CEF Views, a shared library and a helper process.
Keeping that backend largely unchanged entails supporting those pieces.

CEF supports offscreen rendering, which is a promising route to Darterfly
surfaces. The current binding instead uses CEF Views and disables
windowless rendering. Changing only the destination of a pixel buffer
would not satisfy its existing windowing and lifecycle assumptions.

* What to do about TinyCC

Add Clang/LLVM as the native C/C++ toolchain. Keep embedded TinyCC while
that work is qualified. This is a staged migration decision, not a rule
that Darterfly must always carry two compilers.

Darterfly's cc package calls libtcc directly to compile, relocate and run
C code. A clang executable does not implement that API. Removing TCC now
would remove working functionality before the replacement exists.

The native LLVM installation should initially contain the x86-64 target,
Clang, LLD, required archive/object tools and the chosen runtime libraries.
Compiler builtins, C++ standard library, C++ ABI and unwinding support
must be accounted for; installing a frontend alone is insufficient.

A compiler running in an isolated world is still a native Darterfly
program. Its being written in C++ does not turn the Lisp kernel or public
application model into C++. It does require a working native program ABI,
loader, libc interface, threading, filesystem and child-process services.
Those remain the substantive work identified in SELF-HOSTING.org.

* Revised implementation sequence

1. Use the captured Guix source recipe and graph as the initial engine
   build reference. Create a source-building CEF recipe for a compatible,
   explicitly pinned branch. Preserve upstream Nyxt and cl-cef interfaces.
   Export that recipe's SBOM with the same Guix commands.
2. Establish executable loading, argv/env, exit/wait, TLS, foreign runtime
   support and process launch in isolated worlds. Test the actual APIs
   needed by the selected tools, not only symbol availability.
3. Cross-bootstrap a Clang/LLVM toolchain that runs on Darterfly. Prove
   that it compiles, links and executes C and C++ programs locally.
4. Rebuild that toolchain locally, including its native generators. Add
   the selected Rust compiler, GN/Ninja, Python, Node and other measured
   build dependencies. Bootstrap-history versions in Guix's graph are
   provenance; they are not all permanent installed OS requirements.
5. Build the native cl-cef bridge locally. In parallel, compile Nyxt and
   its Lisp dependencies under Darterfly's SBCL and test image persistence.
6. Port and build the selected CEF engine, then prove rendering, input,
   network use, child-process isolation and restart behavior. Qualify
   the display integration rather than assuming Views is already native.
7. Rebuild a changed engine from source inside Darterfly, then repeat for
   an upstream update. This establishes the required ongoing self-hosting
   workflow rather than a permanent external binary dependency.

The large graphs include Linux-specific libraries, packaging tools and
compiler bootstrap history. We must classify each dependency as retained,
adapted, replaced by a Darterfly service, or excluded by a tested build
configuration. Porting every Guix node is neither the plan nor a useful
measure of progress.

* Inventory boundaries still to close

The exports cover the full Guix graph selected by each command. They do
not independently enumerate every vendored Lisp library, Chromium source
subdirectory, bundled Rust crate or library embedded in a binary release.
Those arrive inside origins rather than as separate package nodes.

For a complete component-level inventory of the eventual Darterfly build,
augment the new CEF source recipe with its vendored-source and generated
resource inventory, license notices and selected build graph. Include
Nyxt's pinned Lisp source dependencies and the Darterfly adaptation layer.
Guix remains the authority for the package graph; embedded components
need additional metadata rather than a competing hand-written package list.
