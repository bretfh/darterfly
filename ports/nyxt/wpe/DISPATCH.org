* Ownership

Only the native UI process's GLib thread touches WebKit objects or its
outbound queues. The Lisp socket reader parses replies and records events;
it no longer presents pixels or creates one thread per callback.

Four fixed application workers perform deferred work: one ordered browser
event worker, two scheme-request workers, and one presentation worker.
Scheme requests have a separate lane because a browser event may need a
synchronous JavaScript response that itself needs an internal resource.
The socket reader remains independent of all four workers.

The ordered worker preserves the arrival order of load/title callbacks.
Scheme requests may execute concurrently. This is not a claim that all
upstream Nyxt command threads or window-layout mutations are serialized.
Registry hash tables are synchronized and native IDs share an allocation
lock. Upstream Nyxt sources remain unchanged.

* Output and frames

The native outbox preserves a partially transmitted packet until it is
complete. It never inserts a reply into the middle of pixel bytes. Control
packets retain FIFO order; up to eight are selected before a pending frame
gets a turn. Each pump writes at most 128 KiB and attempts at most sixteen
system calls. EAGAIN or EINTR yields immediately to the main loop, which
continues processing GLib and incoming commands.

Unsent frames coalesce by view. Both native output and Lisp presentation
retain at most 64 pending frames and 64 MiB of queued pixel payload (native
accounting also includes headers). Under pressure, oldest pending frames
are evicted. An active frame is additional to the pending-frame budget;
its maximum payload is 16 MiB. Presentation's existing frame cache retains
its separate 64-view/128-MiB limit. These are queue bounds, not a bound on
total browser RSS; decoding, copies, live WebKit surfaces and GC also use
memory.

The native control queue allows 256 packets and one maximum packet's worth
of bytes (16 MiB plus its header), including an active control packet.
Overflow fails the session instead of losing a control reply. Control age
and active-frame transfer have ten-second limits. An incomplete incoming
packet also has a ten-second limit. Main-loop command batches are bounded.

Deleting a view removes its pending frames on both sides and cancels native
scheme requests belonging to it. A partly transmitted old frame is consumed
and ignored by the reader. Presentation checks the native ID under the
buffer lifetime lock before committing pixels, so delayed work cannot
recreate a deleted view's frame cache.

* Callback and request limits

The event queue holds at most 128 callbacks and 2 MiB of accounted payload;
the scheme queue holds at most 64 requests and 2 MiB. Payload accounting uses
wire lengths, not the implementation-dependent size of Lisp strings and
closures. Fixed workers bound in-flight work outside these queues. Callback
queue overflow is a session failure handled by the existing recovery policy.

The Lisp reply table allows at most 128 pending RPCs. The engine separately
limits live scheme requests and asynchronous JavaScript evaluations to 128
each, and views to 64. Excess engine requests receive an error. Individual
RPC deadlines and scoped reply removal remain in place.

Shutdown closes all work queues, discards pending work and wakes sleepers.
It joins the fixed workers with deadlines alongside the reader/input threads.
The existing application-world exit remains responsible for workers that
cannot finish and for native descendants, descriptors and windows.

* Qualification

Host probes are =check-dispatch-host.lisp= and =check-outbox.cpp=. They check
FIFO behavior, queue accounting/overflow, frame replacement and eviction,
worker wakeup, and exact framing under short writes and EAGAIN. The native
probe verifies that a reply follows an already-started frame and precedes
its newer replacement without corrupting the stream.

Run the host queue probes from the repository root:

#+begin_src sh
guix shell -m manifest.scm -- sh -ec '
  sbcl --no-userinit --non-interactive \
    --load ports/nyxt/wpe/check-dispatch-host.lisp
  c++ -std=c++17 ports/nyxt/wpe/check-outbox.cpp \
    -o /tmp/nyxt-check-outbox && /tmp/nyxt-check-outbox'
#+end_src

The actual-OS harness enables =nyxt-dispatch-checks.lisp= only on its test
disk. It stalls presentation while JavaScript animates a page, checks that
RPCs still complete and frames coalesce, then pauses the actual socket
reader. An incoming JavaScript command must execute during that pause while
native output is backpressured. After resuming, the presentation cache must
converge to a known final frame. Ordered callbacks make synchronous engine
RPCs without creating additional workers.

It uses the resumed dependency-cache disk, not a fresh installation.

* Kernel call retirement exposed by shutdown

The first dispatch run passed the presentation/backpressure probes, then
panicked during clean quit. A stopped caller could resume inside
=port-call-wait= after a late server reply had freed its abandoned call.
The kernel now takes the non-returning thread termination path before
accessing the call again. World stop also retires queued/completed calls
owned by that world and clears stopped-caller pointers from outstanding
server tokens. The server can still finish or discard its abandoned token.

The next run exposed a related case: a call already abandoned before world
stop was freed while its server still held the reply token. The late reply
then stopped a WindowServer worker with EINVAL. Both received and already
abandoned tokens now survive caller stop until their server replies or dies.
The browser harness rejects stopped supervisor workers as well as panics;
a successful application-cleanup marker alone is insufficient.

A dedicated actual-OS probe repeats receive/stop/late-reply/world-removal
200 times, then exercises ten already-abandoned calls, each followed by a
second blocking call. Receiving that second call proves abandonment occurred
before stopping the world. Both late replies must succeed and the world
must disappear. The regression retries only bounded EINTR during init's
driver startup; other receive failures remain errors.

Native process, shared-memory, init, app-world and existing port reclamation
regressions pass 99 distinct checks (102 evaluations, including three checks
repeated when the abandonment case was added). The complete browser run
above also passed after both kernel fixes.

* Still separate

Navigation-generation cancellation, simultaneous deletion/GC stress, hidden
view throttling, detached native-thread reclamation, long resource soaks,
durable profiles, complete interaction and clean installation remain on the
merge checklist. Queue bounds alone do not qualify these properties.
