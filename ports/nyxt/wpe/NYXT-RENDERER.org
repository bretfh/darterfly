#+title: Nyxt's native WPE renderer
#+date: 2026-10-19
#+startup: overview

* What runs

Nyxt's normal browser initialization, web buffers, status and message
panels, command dispatch and URL prompt run in an isolated Lisp world.
The WPE extension presents their software-rendered contents through the
existing Darterfly WindowServer. Pointer and keyboard events travel back
through Nyxt's keymaps and into WebKit when Nyxt does not consume them.

The renderer lives in this port directory; app registration lives in
src/apps. This step changes no pinned Nyxt application source. It
specializes Nyxt's existing renderer classes and foreign interface rather
than replacing its commands or prompt UI.
WPE uses the existing source port and shared native CRT/libsa.

See [[file:app-evidence.json][the normal-app qualification]],
[[file:qualification-logs/nyxt-app-guest.log][its guest transcript]], and
[[file:qualification-logs/nyxt-app-origin.log][the independent HTTPS origin log]].
The run passed ordinary Dock launch, instance reuse, browser interaction,
Ctrl-Q with zero exit status, child/window cleanup, Dock relaunch and a
second clean exit. Host regressions passed 87 checks; actual-OS regressions
passed 43 native-process checks and 9 app-world/WindowServer checks.

The earlier [[file:browser-evidence.json][browser record]] retains the pre-application
milestone. The [[file:nyxt-build-evidence.json][core-build record]] describes the separate clean-disk
source build. Neither is relabeled as the current normal-app result.

* Architecture

#+begin_example
Darterfly's normal init and existing world/process services
  |
  +-- Nyxt / SBCL world
  |     upstream commands, modes, buffers and persistent Lisp history
  |     nyxt-renderer.lisp specializes the renderer interface
  |       |
  |       +-- named Unix socket --> native WPE UI world / GLib loop
  |       |                          +-- trusted Nyxt UI WebProcess
  |       |                          +-- web content WebProcess(es)
  |       |                          +-- NetworkProcess / libsoup / TLS
  |       |                       <-- BGRA frames, events, JS results
  |       |
  |       +-- Layer world client --> existing WindowServer service
  |                               <-- keyboard / pointer events
  |
  +-- existing WindowServer --> framebuffer
#+end_example

Nyxt's trusted panels share a WebProcess using WebKit's related-view API.
Web content uses separate WebProcess instances. All use the same existing
native loader, libsa, allocator, pthreads and BSD process facilities.
Presentation runs inside the Nyxt app world. Its Layer client uses the same
world-facing WindowServer service as other isolated applications. The old
Nyxt Windows broker and its second socket have been removed.

WPE owns its GLib loop on one native thread. Lisp callbacks run separately
from the engine reply reader, allowing synchronous JavaScript requests
inside Nyxt callbacks. Writes are serialized. The asynchronous evaluation
API discards return values, including Promises, while reporting errors.
Synchronous results use Nyxt's JSON representation, including hash tables.

Frames are copied from WPE's premultiplied BGRA buffers, converted to RGBA
and committed as ordinary layers. This is an initial transport with full
frame copies. Shared surfaces, damage tracking and frame coalescing remain
performance work.

* Runtime fixes exposed by the browser

The SBCL spawn bridge now inherits the environment when its environment
argument is NULL. An explicitly empty environment stays empty. This is
required for CA trust and font configuration to reach the WPE processes.
The native guest checks exercise both cases.

The shared passwd/group functions now resolve the default APFS owner,
uid 501 and gid 20, as darterfly/staff, alongside root. Nyxt's NFiles history
writer reads and preserves ownership. These entries match the existing
single-user filesystem defaults; they are not a new account system.

A received world RPC can be abandoned by a signal after its service has
already consumed socket bytes. Retrying that read loses framing. Both
ends of this adapter therefore use short nonblocking transfers and defer
signals across each transfer, restoring the mask before waiting. The Lisp
end also pins the buffer and defers GC during that call. This is a scoped
transport fix; general world-RPC cancellation semantics remain separate
runtime work.

The normal application also exposed a shared stdio bottleneck. The old
fgets implementation made read/seek service calls for every PEM line in
the system CA bundle. OpenSSL loaded that bundle on WebKit's main thread,
which exceeded its responsiveness deadline and was terminated by WebKit.
Shared libsa now buffers input across fgets, fgetc and fread, preserving
logical positions, pushback, seek/flush behavior and caller-owned buffers.
The native runtime regression exercises those contracts, pipes and a
4,096-line file, including after rebuilding the probe inside Darterfly.
Certificate validation and WebKit's watchdog policy are unchanged.

The browser test explicitly allocates 8 GiB guest RAM and a 2 GiB supervisor
heap. The regular boot configuration retains its existing defaults. These
sizes are test configuration, not a measured minimum browser requirement.

* Protocol and ownership

Each packet has six little-endian unsigned 32-bit words followed by bytes:
operation, object ID, request ID, argument A, argument B, payload length.
Payloads are limited to 16 MiB and frame dimensions to 2048 per axis.
Strings are UTF-8. Wire packets are never read as Lisp forms.

Engine operations cover view creation/deletion, navigation, HTML loading,
JavaScript, resize, keyboard/buttons, custom schemes, zoom, history and
shutdown. Events carry frames, load state, titles, resource requests and
errors. Presentation operations are now local Lisp calls which create
windows, attach/detach buffer layers, present frames and release buffers.
The presentation session bounds its window/frame caches. World teardown
reclaims its WindowServer client through the existing service.

Nyxt's internal Lisp callback scheme is accepted from its own UI and
internal documents. Ordinary web content cannot invoke those callbacks.
The Lisp request reader also binds *read-eval* to nil. Qualification tries
the same registered callback from a trusted status panel and an HTTPS page.
This check is a boundary regression, not a complete browser security audit.

* Recovery ownership

The Nyxt app job uses init's existing restart-on-crash policy: two automatic
retries within ten minutes, then =:failed=. A manual launch resets the budget.
Normal quit stays stopped. Recovery creates a fresh Lisp application world;
its native descendants and WindowServer client are reclaimed by the existing
OS services. It does not preserve unsaved tabs or forms.

Engine loss, process-failure events and timed-out liveness/transport operations
fail the session. Init also checks progress from outside the app, so a paused
or stuck Lisp world cannot keep its own supervisor waiting indefinitely.
Shutdown bounds its sends, exit polling and thread joins. See
[[file:RECOVERY.org][the recovery design and actual-OS reproduction]] for policy, limits and the
small WebKit NetworkProcess notification patch. Nyxt sources remain unchanged.

* Installed application and normal launch

The optional package entry function in application-image.lisp installs a
Nyxt application stub, the renderer extension, pinned Nyxt sources, native
engine/dependencies and CFFI toolchain. It consumes the existing cross-build
products; a fresh, self-contained build installer remains separate work.
It does not install fixture certificates or qualification hooks.

The Dock includes Nyxt when that application stub is installed. Clicking it
submits an ordinary init job, using the system core and an explicit 2 GiB
app-world budget. Further clicks activate the existing instance. Terminal
and Editor retain their 512 MiB defaults. The entry point loads upstream
Nyxt with the renderer extension and uses the installed system CA store.
OCICL remains the source of Lisp-side TLS. Diagnostics go to
/tmp/nyxt-application.log and /tmp/nyxt-engine.log.

The reusable loader can compile Lisp sources and CFFI helpers using the
installed TCC/LLD and shared libsa. The desktop qualification reuses the
existing dependency FASLs; it is not another clean-source build.

* Lifetime fixes

Asynchronous prompt producers may finish after the prompt view is deleted.
Renderer submission and deletion now share a per-buffer lock, and obsolete
JS submissions are discarded. A page's asynchronous JavaScript error is
reported without poisoning the global transport-failure flag. The browser
checks explicitly exercise a late update after prompt deletion.

Normal shutdown closes the display session, cancels transport, polls for
engine exit and joins reader threads with deadlines. World teardown owns
remaining descriptors and callbacks. The renderer implements upstream
Nyxt's uninstall interface; the app waits for that interface before returning.
The recovery policy is described above; concurrent event ownership and
queue bounds remain separate gates.

* Remaining work toward everyday use

See [[file:MERGE-READINESS.org][the source-reviewed integration plan and acceptance gates]].

The remaining work includes bounded event queues, fresh-install
qualification, persistent WebKit sessions and browser-database locking.
WPE's session is currently ephemeral. Nyxt's Lisp history writer executes, but durable
browser state across reboots is not qualified by this test.

Complete the renderer API for downloads, clipboard, pointer motion/wheel,
window resize/close controls, named JavaScript worlds and user scripts.
Qualify buffer switching, error pages, broader site compatibility and
media. Current tests prove navigation and text interaction with controlled
HTTPS content; they do not establish compatibility with arbitrary sites.

The successful transcript still contains a background prompter network
timeout and an OCICL warning about a certificate with a nonpositive serial
number. Navigation completed, but background network activity is not yet
fully controlled by the test's search-suggestion setting. These warnings
remain visible in the saved log and need follow-up before daily use.

The engine remains cross-built from pinned upstream sources. This work
uses the existing native compiler path, but does not claim that the entire
WebKit build can already be reproduced inside Darterfly.
