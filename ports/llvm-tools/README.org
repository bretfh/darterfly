#+title: Native LLVM archive and TableGen tools
#+date: 2026-10-18
#+startup: overview

* Placement and implementation

Upstream LLVM 19.1.7 llvm-ar, llvm-tblgen and clang-tblgen are built as
static executables for isolated Darterfly worlds. They use the same Low
libsa, allocator, static TLS, C++ runtime and BSD descriptor/process
services as native Clang and LLD. This port adds no second libc or TLS
implementation and changes no upstream LLVM sources.

llvm-ar has a small main wrapper for LLVM's ToolContext entry interface.
The same executable, named llvm-ranlib, selects upstream's ranlib entry.
Both TableGen programs retain their upstream main functions and complete
source/library lists. CMake derives those lists from the upstream targets,
including LLVM's Basic and Common generator object libraries. The host
TableGen executables remain separate during cross compilation.

* Build the initial seeds

The [[file:../clang/README.org][Clang recipe]] supplies the pinned source, sysroot and configuration.
The aggregate recipe prepares host generators and the selected C++ runtime
once, then builds all three tools. For a fresh worktree, first prepare the
normal Darterfly image and the Clang/LLD seeds described in their guides.

#+begin_src sh
cd ~/git/cl/darterfly-nyxt
guix shell -m manifest.scm -- python3 tools/build-native-llvm-tools.py
make test-native-llvm-tools-guest
#+end_src

Use --skip-prerequisites only when those dependencies are already built.
For a single tool, the common recipe accepts --tool llvm-ar,
--tool llvm-tblgen or --tool clang-tblgen. Existing Clang and LLD entry
points remain supported.

Each tool has an executable, symbol map and provenance JSON under
build/llvm-tools. The corresponding .o.inputs.json under build/clang/bin
records the initial archive/object inputs. Host LLD resolves those inputs
into a relocatable object; the Lisp linker adds shared libsa and performs
the final executable link. These are imported bootstrap seeds. Running
them locally is not yet rebuilding their own sources locally.

* Actual-OS qualification

The harness boots Darterfly's kernel and Lisp image in four-vCPU, 4 GiB
QEMU/KVM with a disposable APFS disk. It stages the executables, upstream
sources and comparison tables explicitly. It does not install the tools
into the user's persistent disk or qualify physical hardware.

All 23 guest assertions passed on 2026-10-18, including explicit symbol
index removal and reconstruction with ranlib. The guest tests cover:

- Independent native startup of all three tools and upstream ranlib.
- LLVM attribute, Clang declaration and x86 register generation compared
  byte for byte with the pinned host build's generated tables.
- A local TableGen input edit introducing a new compiler attribute. The
  generated definition is required by a C++ program compiled in the guest.
- Native archive creation, listing, deterministic contents, extraction,
  replacement, deletion and indexing; response files and paths with spaces.
- Native LLD linking the generated-header program with a selected archive
  member. Another member has an unresolved symbol and must stay unused.
- Running the result in another native world; replacing an archive member
  changes the next executable's result from 42 to 43.
- Missing-member and malformed-TableGen diagnostics, subsequent successful
  work, and reaping every native child.

The host tables are comparison oracles only. The C++ program includes the
headers generated in /tmp by the native tools, including its new attribute.
Neither a failed generation nor a failed compile falls back to the host.
The transcript is [[file:../../build/native-llvm-tools-guest.log][build/native-llvm-tools-guest.log]].

* First complete local source rebuild

Start with clang-tblgen as the first closed LLVM-tool rebuild. Its seed is
about 1.9 MiB, and it exercises LLVM Support and TableGen without bringing
in the whole x86 code generator. Its source closure still includes those
libraries and the selected C++ runtime, not only the Clang emitter files.

Derive a per-translation-unit build manifest from the pinned configuration.
Keep target defines, include ordering, language options and exception/RTTI
settings explicit. Translate paths into the guest source/sysroot layout;
do not pass host include paths to the native frontend. Clang currently
runs through -cc1, so driver options need deliberate frontend equivalents.

An initial Lisp runner can consume that manifest, schedule generator jobs,
compile objects, archive libraries with llvm-ar and link with native LLD.
That is an execution milestone. Closing self-hosting also requires local
regeneration of the manifest and configuration headers. Keep those two
claims separate in the evidence.

Acceptance for this first tool: rebuild every selected input from source,
run the new clang-tblgen on the same declaration and malformed-input tests,
and compare its generated output. Then use that rebuilt generator in a
second compiler build. Preserve logs and input hashes so imported objects
cannot silently survive into an alleged complete local rebuild.

* What this closes, and what remains

The selected archive and generator operations can now run on Darterfly's
existing native runtime. This supplies two necessary parts of LLVM's local
build chain. It does not establish a complete compiler source rebuild.

1. Make the configuration and dependency graph regenerable locally. A
   Lisp build runner can execute compiler, archiver, linker and generator
   jobs; it must also account for configuration checks and generated
   inputs currently supplied by CMake, Ninja and Python.
2. Compile all selected runtime and tool sources inside Darterfly. Start
   with these smaller tools, then Clang and LLD. Regenerate all required
   tables, not only the three families qualified here. Record peak memory,
   disk space, elapsed time and failures on the larger translation units.
3. Use the locally rebuilt tools for another source build and functional
   test stage. Record imported inputs and reproducibility separately.
4. Close Nyxt's foreign dependencies and the chosen engine's platform and
   build requirements. These tools do not supply dynamic loading, browser
   IPC, shared-memory coherence, graphics integration or Chromium's build
   generators and scripts.

Thin archives, non-ELF library modes, all generator backends, LTO and large
compiler archive/link workloads remain unqualified. This milestone does
not add a native Clang driver; compilation still invokes -cc1 explicitly.
The [[file:../nyxt/SELF-HOSTING.org][self-hosting plan]] keeps browser and compiler acceptance separate.
