#+title: Native Clang frontend on Darterfly
#+date: 2026-10-18
#+startup: overview

* Scope

This port brings upstream LLVM/Clang 19.1.7 to the existing native-world
ABI. The seed contains the x86 backend and Clang's unchanged =cc1_main=.
A small entry point accepts =clang -cc1=. There is no compiler service on
the host, and no Linux loader or second libc inside the executable.

The seed is cross compiled. Its parser, semantic analysis, optimization
passes and object writer subsequently execute in a Darterfly world.
The system's Lisp linker links generated objects with the same Low libsa,
startup, allocator and static TLS used by standalone TCC. LLVM libc++,
libc++abi and libunwind supply the C++ library and exception machinery.

This is not a locally rebuilt Clang distribution or a browser port. The
full driver, build generators and LLVM source rebuild are subsequent
milestones. [[file:../lld/README.org][Native ELF LLD now also links and runs guest-compiled C++]].
The tests distinguish those claims from native compilation.

* Build and bootstrap inputs

#+begin_src sh
cd ~/git/cl/darterfly-nyxt
guix shell -m manifest.scm -- python3 tools/build-native-clang.py
make test-native-clang-guest
#+end_src

=--skip-prerequisites= reuses the existing C++ runtime and host generators
while developing the port. It must not be used to disguise missing inputs
in a fresh bootstrap.

The source is the same Guix LLVM 19.1.7 origin recorded in
[[file:../cxx/README.org][the C++ runtime manifest]]. The host generator environment is recorded in
[[file:host-manifest.scm][host-manifest.scm]], with channels in [[file:channels.scm][channels.scm]]. GCC 14 builds the upstream =llvm-tblgen= and
=clang-tblgen= for Guix. The target frontend is compiled with the main
manifest's Clang. Host include-search environment variables are removed
from target compilations.

The cross configuration uses CMake's FreeBSD platform selection to obtain
its Unix/ELF build rules. The actual compiler target is explicitly
=x86_64-unknown-none-elf= with =__darterfly__=. It neither selects the
FreeBSD C headers nor changes Darterfly's syscall ABI. A named Darterfly
CMake platform is a future packaging cleanup.

The host LLD resolves upstream static archives and COMDAT sections into
an ELF relocatable object, retaining the closure reachable from =main=.
The final executable is made by =link-native-program= using Low's freshly
built libsa. No host startup objects or host C/C++ libraries are linked.
The generated =build/clang/provenance.json= records source, configuration,
compiler version and the final executable hash; the intermediate object's
=.inputs.json= records the archive inputs.

* Runtime additions

The shared libsa provides the additional declarations and C-locale
operations needed by LLVM and libc++ streams. Its numeric scanner and
allocation-backed formatting reuse the existing parsers and formatter.
C++ locale names other than C, POSIX and the empty default fail explicitly.
Wide conversion currently implements the single-byte ASCII C locale;
unrepresentable input returns EILSEQ. It is not a UTF-8 locale.

The runtime build now includes upstream stream, locale, call-once and
random-device sources. Random-device reads Darterfly's existing
=/dev/urandom=. File streams use the existing descriptor service. This
source selection is not a complete libc++ filesystem library.

Some interfaces remain deliberately limited: filesystem capacity queries
return ENOSYS, child resource accounting is absent, wide printf supports
numeric conversions, and scanf does not yet implement scansets. These
are not evidence of a complete POSIX or C library. The pre-existing time
formatting, process-group, exec and mapping limitations also remain.

Native ELF programs receive an 8 MiB initial stack, matching the existing
Lisp-world stack and libsa's reported stack limit. Executable validation,
separate page tables and the static TLS path are retained.

* Native compilation interface

#+begin_src lisp
(darterfly/cc:compile-native-cxx
 "/usr/bin/clang" "/Users/darterfly/example.cpp" "/tmp/example.o")

(darterfly/cc:compile-c
 "/usr/src/darterfly/src/libsa/crt0.S" "/tmp/crt0.o" :compat nil)

(darterfly/cc:link-native-program
 "/tmp/example"
 '("/tmp/crt0.o" "/usr/lib/cxx/runtime.o" "/tmp/example.o"))

(sb-ext:run-program "/tmp/example" nil :search nil
                    :output *standard-output* :error *error-output*)
#+end_src

The compiler helper supplies the static target ABI and explicit libc++,
libsa and Clang resource include directories. It accepts additional include
paths, definitions, a working directory and diagnostic streams. Failed
compilation removes the output, including an old object at the same path.
This interface does not invoke a host compiler when compilation fails.

* Acceptance tests

[[file:../../tests/native-clang.lisp][The guest harness]] boots Darterfly under QEMU/KVM with the native compiler,
headers, runtime object and source files on a disposable APFS disk.
The test stages these files explicitly; this does not install Clang into
an existing user disk or every normal image. It exercises:

- Native frontend startup and version output.
- C++ source to ELF object inside the OS.
- Final linking inside the OS with a freshly built shared libsa and CRT.
- Execution with constructors, containers, streams, exceptions and a thread.
- Invalid source diagnostics and stale-output removal.
- Recompilation from another working directory with a changed definition.
- Compilation of upstream LLVM's Itanium demangler and its caller, followed
  by linking and running that locally rebuilt compiler component.
- Reaping of native processes after both successful and failed compiles.

The expanded [[file:../../tests/native-cxx.lisp][C++ runtime guest test]] separately exercises streams, C-locale
conversion, numeric parsing and random-device access along with the earlier
constructor, exception, TLS, destructor and isolation checks.

On 2026-10-18, all 13 native frontend guest assertions and all 17 expanded
C++ runtime assertions passed. The frontend transcript is
=build/native-clang-guest.log=. See [[file:../nyxt/VALIDATION.org][the validation record]] for regression
results and the known unrelated host-suite failure.

The seed is approximately 50.2 MiB, below the loader's 128 MiB bound. Its
partial-link object has over 348,000 sections; the Lisp ELF reader now
handles extended section counts and symbol indices. A native-world
startup fault also exposed an existing dladdr path that assumed a kernel
ELF mapping. That path now reports missing symbols when no mapping exists,
instead of dereferencing address zero.

* The route to rebuilding LLVM and the browser

1. Qualify this frontend on larger upstream translation units, including
   resource limits, diagnostics, file streams and failed output writes.
2. Native LLD now handles the tested archive, COMDAT and partial/final
   links on the same runtime. Bring up archive/object utilities and
   qualify larger compiler links. Retire host LLD from the complete seed
   rebuild loop, including the LLVM archive resolution step.
3. Build and run LLVM's TableGen tools in native worlds. Replace the host
   generators and regenerate the target's configured headers and tables.
4. Supply a native build runner. A Lisp runner may initially execute a
   recorded build graph; a complete rebuild must regenerate that graph
   locally and account for CMake/Ninja/Python or their replacements.
5. Rebuild the frontend and its runtime from source on Darterfly, use that
   compiler to rebuild them again, and compare and test the generations.
6. Port the remaining Nyxt dependencies and CEF/Chromium platform layer.
   A compiler closes a prerequisite; it does not supply an engine's IPC,
   sandboxing, event loop, shared-memory, graphics or dynamic-loader APIs.

Keep Nyxt and its existing renderer integration close to upstream.
Browser-engine source rebuilding remains a separate acceptance gate, as
laid out in [[file:../nyxt/SELF-HOSTING.org][the browser self-hosting plan]].
