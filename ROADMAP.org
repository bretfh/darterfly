#+TITLE: Darterfly roadmap

* Direction
Build a dependable, self-hosting Lisp workstation on QEMU and one precisely
identified physical machine, then expand its applications and hardware support.
Darterfly's advantage is a coherent system that users can inspect, modify, and
rebuild while using it. Broad Linux/BSD/macOS/Windows parity is a multi-year
platform and ecosystem effort. Progress is measured by working user workflows
and failure guarantees, not by the number of subsystems with implementations.

The actionable backlog is in [[file:TASKS.org][TASKS.org]]. Release commands, evidence formats, and
reproduction limits are in [[file:release/README.org][release/README.org]]. The platform matrix is in
[[file:release/PLATFORMS.org][release/PLATFORMS.org]]. A test's presence is not evidence that it passed.

* Starting point
The repository already contains a Lisp boot/kernel/runtime stack, SMP, separate
world address spaces and IPC, APFS persistence, networking, desktop applications,
and self-building generations. Existing tests cover failed-generation fallback
and torn commits. Strengthen those foundations rather than replacing them.

The C runtime still has fork/exec and identity/job-control placeholders
(src/libsa/unistd.c). World service requests currently create individual threads
(src/run/run.lisp), and executable mappings need a defined protection policy
(src/kern/i386/world.lisp). nREPL has a key check but uses raw TCP and Common Lisp
random for its generated key (src/nrepl/nrepl.lisp). Historical arraniz results
include roughly 70 ms full-frame redraw; that is not an interactive frame-rate
measurement. These observations motivate the ordering below and must be
rechecked as implementations change.

* 1. Reproducible, measurable release baseline
Pin dependencies; build from a captured source tree with private caches; retain
source identity, tool and firmware versions, image hashes, command lines, test
outcomes, and serial logs. Separate host checks, guest integration, destructive
recovery, and physical qualification. Measure boot, memory, GC, rendering,
storage, network, and responsiveness with raw samples and tail statistics.

Acceptance: a clean checkout produces an identifiable image using a recorded
recipe, and failures can be reproduced from its captured inputs. Full-image
bit-for-bit reproducibility is a separately measured property. Physical support
claims require dated results tied to the tested generation and machine.

* 2. Complete the world/application boundary
Specify the trusted system world and per-application filesystem, network,
device, and debugging authority. Make isolated worlds the ordinary application
launch path. Bound memory, threads, ports, descriptors, requests, and queues.
Add cancellation and backpressure without serializing unrelated blocked I/O.
Audit pointer validation, overflow, executable mappings, object lifetime,
partial allocation failure, and SMP races. Support JIT compilation under an
explicit executable-memory policy.

Acceptance: a hostile or buggy application cannot corrupt another world,
consume resources without limit, or make the desktop unrecoverable. Existing
world supervision and watchdogs are useful foundations, not substitutes for
resource and authority boundaries.

* 3. Trustworthy storage, installation, and updates
Extend existing torn-commit and failed-generation tests to write/flush fault
injection, reordered writes, full disks, device errors, interrupted installation,
and pruning. Specify durability contracts. Add offline checking, recovery media,
backup/restore, authenticated update manifests, and signing-key lifecycle.
Include settings and data-schema compatibility in rollback policy.

Acceptance: interrupted updates leave a recoverable old or new system, and
acknowledged durable user data survives the documented failure model.

* 4. Usable software platform
Keep the native Lisp APIs central. Publish a supported POSIX/C profile and
replace placeholder success returns with real behavior or honest errors.
Drive executable loading, spawn/exec/wait, pipes, descriptors, signals, PTYs,
polling, file locking, and mappings with real ports. Decide fork semantics
explicitly. Initial targets: shell, build tools, Git, HTTPS client, SQLite, and
a terminal editor. Add package dependencies, clean builds, signatures,
install/remove/upgrade behavior, and runtime tests.

Acceptance: acquire a project, resolve dependencies, build, test, and install it
entirely inside Darterfly. Browser dependency research starts here, before
committing to a long porting effort.

* 5. One complete physical workstation
Qualify display, keyboard, touchpad, USB, NVMe, wired networking, Wi-Fi, audio,
battery, thermal behavior, shutdown, and suspend/resume on the reference machine.
Exercise reconnects, hotplug, packet loss, malformed traffic, and certificate
rejection. Secure remote development and deployment; use a cryptographic random
service for secrets with specified initialization and failure behavior.

Acceptance: a week of normal work, connectivity changes, unplugging devices,
and restarts without routine recovery through another OS.

* 6. Coherent, responsive desktop
Measure rendering, allocations, locks, and GC interaction; improve damaged-region
rendering before choosing a GPU strategy. Budget typing, scrolling, window
movement, and launch latency. Complete file management, dialogs, clipboard,
drag-and-drop, settings, notifications, locking, and crash recovery. Establish
text shaping, input methods, keyboard navigation, and accessibility interfaces.
Make inspect-widget -> source -> edit -> apply -> undo/recover a polished flow.

Acceptance: predictable daily work and an exceptional live development experience.

* 7. Ecosystem and support commitment
Choose a maintained browser strategy based on a dependency/portability study;
remote applications may bridge gaps. Expand hardware, acceleration, multimedia,
printing, Bluetooth, and developer tools according to real users' needs.
Publish an SDK, compatibility policy, release channels, security-update process,
and supported hardware list. Give contributors bounded ownership and clear tests.

Acceptance: another developer can build, distribute, and maintain an application
without needing the original author's explanation of the internals.
